# Synthetic baseline data

The generator is implemented in `backend/app/generation/` and always uses seed
`20261022`. It generates deterministic string IDs, valid foreign-key relationships,
and goal progress through the shared key-result progress service.

## Generate the starter dataset

From `backend/`, run:

```powershell
.\venv\Scripts\python.exe -m app.generation --scale starter
```

Starter scale contains 30 employees, 5 managers, 100 goals, and 200 check-ins,
plus the related cycles, key results, competencies, feedback, reviews,
development plans, evidence, and approvals. The default output is
`backend/generated/starter/`.

The output contains CSV and JSON files for baseline tables, an aggregate JSON
export, derived goal progress, a SQL seed script, and a generation summary.
Anomaly fixtures are kept in `anomaly_fixtures.json`; labels and expected
decisions are isolated in `ground_truth.csv` and `ground_truth.json`. A separate
`validation_report.json` records validated row counts and foreign-key checks.
Neither anomaly file is included in baseline table exports or the SQL seed.

The prepared full-scale files are available read-only through the Data & Exports
API. `GET /api/v1/data-exports` verifies the CSV/JSON row counts and SQL insert
counts against the prepared validation report and returns SHA-256 checksums.
Download files with `GET /api/v1/data-exports/{csv|json|sql}/{filename}`;
README, schema, and data dictionary files use the `docs` format. These requests
serve the existing `generated/full/` snapshot and do not regenerate or modify
PostgreSQL records.

The output writer refuses to replace an existing directory unless its complete
file set matches the newly generated bytes exactly. Repeated generation with
the same seed and scale has identical data and checksums. The full-scale output
also preserves the starter-scale prefix: its first 30 employees, first 5
managers, and every starter row with a shared primary key have identical values.

## Load the starter dataset into PostgreSQL

After confirming `backend/.env` points to the local `performtrack_db`, run from
`backend/`:

```powershell
.\venv\Scripts\python.exe -m app.generation --scale starter --load-db
```

The loader verifies the active database name, appends rows in foreign-key order
inside one transaction, and skips existing rows only when every generated value
matches. A conflicting existing primary key aborts and rolls back the
transaction; existing records are never updated or deleted. Anomaly fixtures and
ground truth are never loaded into PostgreSQL.

The full scale (3,000 employees, 500 managers, 10,000 goals, and 20,000
check-ins) is supported by the same generator. To prepare a full export that
preserves the currently stored starter records, run from `backend/`:

```powershell
.\venv\Scripts\python.exe -m app.generation --scale full --prepare-from-db
```

This mode reads the configured `performtrack_db` in a read-only transaction,
uses persisted rows and existing bridge/approval relationships in preference to
scale-dependent generated variants, validates the merged full snapshot, and
writes exports to `backend/generated/full/`. It does **not** load or modify
PostgreSQL. The full-scale database load remains a separate, approval-gated
operation.

To explicitly approve an insert-only full-scale load after reviewing the
prepared dataset, run from `backend/`:

```powershell
.\venv\Scripts\python.exe -m app.generation --scale full --load-db --confirm-full-load
```

The command confirms the configured and live database are both
`performtrack_db`, prepares and validates a read-only merge that preserves
existing rows, exports the merged CSV/JSON/SQL files, and inserts only missing
rows in a transaction. Conflicting existing values abort the transaction;
existing PostgreSQL records are never updated or deleted. Full-scale loading
requires the explicit `--confirm-full-load` flag.
